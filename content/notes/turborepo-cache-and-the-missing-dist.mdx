Some bugs are interesting because they're hard. This one was interesting because
both answers were correct at the same time: the build passed on my machine and
failed in CI, from the same commit, with no flakiness and no race.

## The setup

PowerMySport is a Turborepo monorepo — three Next.js applications over a shared
types package. The package compiles TypeScript to `dist/`, and the applications
import from it. Turborepo caches task results so an unchanged package doesn't
get rebuilt on every run, which is the entire point of using it.

The cache works on a simple contract. Turborepo hashes a task's inputs, and if
it has seen that hash before, it skips the work and restores the recorded
outputs instead. Both halves matter: skip the work, **restore the outputs**.

## What went wrong

The `build` task declared its outputs like this:

```json
"build": {
  "dependsOn": ["^build"],
  "outputs": [".next/**", "!.next/cache/**"]
}
```

That's correct for the Next.js applications. It is silently wrong for the shared
package, which doesn't produce `.next/` at all — it produces `dist/`.

So Turborepo cached the package's build as a task that produces *nothing*. Not
as an error: as a legitimate, successful, empty result. And a cache entry
recording nothing restores nothing.

## Why it only failed in CI

On my machine `dist/` was already on disk from an earlier run. A cache hit
skipped the compile, restored nothing, and the stale-but-present `dist/` was
still sitting there — so the import resolved and the build passed.

CI starts from a clean checkout. It restored the same cache entry, skipped the
same compile, and restored the same nothing — except there was no `dist/` on
disk to fall back on. Every application importing the package failed to resolve
it.

The two environments weren't disagreeing. They were both faithfully reporting
what they saw. The difference was that one had a leftover artifact hiding the
problem.

## The fix

One line:

```json
"outputs": [".next/**", "!.next/cache/**", "dist/**"]
```

## What I took from it

The failure was invisible locally *because* my machine had more state than CI
did. That's the general shape: a cache that's wrong about what it produced is
worse than no cache at all, because it fails only where you can't watch it.

Two habits came out of this. First, when a task is cached, I now check what the
cache thinks the outputs are, not just whether the task succeeds. Second, when
local and CI disagree and neither is flaky, the question isn't "which one is
right" — it's "what does my machine have that CI doesn't."

The comment explaining this now lives in `turbo.json`, directly above the line
that fixes it. It reads, in part: *that is not hypothetical — it is how a green
local build and a red CI build coexisted here.*
